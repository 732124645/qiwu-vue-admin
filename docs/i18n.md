# 国际化：词条、语言切换与时区

当前支持 `zh-CN` 和 `en-US`，默认 `zh-CN`（`LOCALES` / `DEFAULT_LOCALE`）。界面、校验、系统消息使用词条；用户填写的业务内容按原文保存和显示。

## 在哪里新增词条

| 内容             | 位置与约定                                                                                                            |
| ---------------- | --------------------------------------------------------------------------------------------------------------------- |
| 桌面界面公共文案 | `apps/web/src/locales/{zh-CN,en-US}/<namespace>.json`；如 `crud.json` 的内容进入 `crud.*`                             |
| 项目界面与菜单名 | `apps/web/src/locales/{zh-CN,en-US}/<domain>.<business>.json`；项目自己增加词条到本领域片段                           |
| 校验消息与字段名 | `packages/shared/src/i18n/{zh-CN,en-US}/validation.json`、`field.json`；项目字段放 `modules/<domain>.<business>.json` |
| 服务端错误与提示 | `apps/server/src/i18n/{zh-CN,en-US}/`；项目可用自己的 `<domain>.<business>.json` 片段，避免占用平台词条               |
| 种子的共享显示名 | `packages/shared/src/i18n/{zh-CN,en-US}/seed.json`；数据库存 `seed.*` 键                                              |
| 移动端界面       | 有 `mobile/` 时放 `mobile/src/locales/{zh-CN,en-US}/`；生成模块也用自己的 `<domain>.<business>.json`                  |

`mergeLocaleFile()` 对不带点的文件名添加命名空间；带点的模块片段直接深度合并根对象。例如 `erp.sale-order.json` 应包含完整对象层级，而不是再包一层文件名：

```json
{
  "erp": { "saleOrder": { "entity": "销售订单" } },
  "menu": { "erp": { "saleOrder": "销售订单" } }
}
```

对应 en-US 文件保留相同键，填入人工校对的译文。共享字段片段可包含 `{"field":{"erp":{"saleOrder":{"orderNo":"订单号"}}}}`。页面用 `t('erp.saleOrder.entity')`，schema 通过 `fieldDomains` 注册字段领域，校验消息返回 `validation.*` 键；服务端不另建自己的 `validation.json` / `field.json` 副本。

`apps/web/src/core/i18n/index.ts` 用 glob 加载并合并；`CoreI18nModule` 的 `LocaleFilesLoader` 从 `i18nDirs()` 递归加载。构建路径由 `core/paths.ts` 管理，服务端构建会携带共享词条。重复定义同一键会被检查拒绝，即使值相同也不要在 web/server 再复制 shared 的键。

## 语言如何选择与切换

服务端 `resolveLocale()` 顺序：支持的 `?lang=` → `Accept-Language` → 已登录用户 `locale` → `zh-CN`。`matchLocale()` 先匹配完整标签，再匹配语言前缀，如 `en-GB` 对应 `en-US`；`Accept-Language` 按 q 值及原顺序选择，排除 q=0，不支持的标签跳过。请求显式语言存 CLS；非 HTTP 场景可用 `currentLocale()` 回落到 principal 和默认语言。

桌面端 `detectLocale()` 顺序：localStorage 的 `qw.locale` → 浏览器语言 → `zh-CN`。`setLocale()` 更新 vue-i18n、dayjs、`<html lang>` 与响应式第三方语言引用；HTTP 客户端每次发请求用当前语言设置 `Accept-Language`。`useLocaleStore.set()` 在已登录且不处于强制改密状态时串行保存到 `PUT /api/iam/profile/locale`，使异步通知可以使用账号语言；保存失败不撤销本地切换。

| 第三方界面   | 接入点                                                 |
| ------------ | ------------------------------------------------------ |
| Element Plus | `elementLocale` → `el-config-provider`                 |
| dayjs        | `setLocale()` 调用 `dayjs.locale()`                    |
| ECharts      | `chartLocale` → `QwChart` 初始化语言及 key，切换后重建 |
| form-create  | `formLocale` → 渲染器及设计器语言                      |

新组件沿用这些响应式接入点。语言检查只能覆盖静态词条与部分字面量引用，不能证明第三方组件所有交互已翻译；切换后需要检查日期控件、图表、表单设计器及项目自定义界面。

## 数据库键与用户文本

种子角色、部门、岗位等名称可以存 `seed.*`，菜单存 `menu.*`，前端用 `tx(key)`：存在词条就翻译，否则回显原文。`useCrudForm` 对种子名称显示译文，名称未改变时保存原键；`seedKeysLike()` 支持按种子译文搜索。

字典的 `label_i18n`、参数与菜单等的 `name_i18n` 是按语言存储的 JSON。前端 `localized(text, fallback)` 优先取当前语言的非空值，再用 `tx(fallback)` 回落。

订单标题、公告正文、用户名、联系人等用户数据保持原文。`refName(id, name)` 特意不调用 `tx()`，避免一个恰好长得像词条键的用户名字被替换成系统译文。只有明确采用种子键约定的字段才用 `tx()`，不能强制翻译所有数据库字符串。

通知模板按渠道的 `(code, locale)` 行选择，参数按接收人语言渲染，详见[通知文档](notify.md)。已经保存的通知标题和正文是发送时的文本，切换界面语言不会重新翻译历史通知。

## 时间与时区

数据库连接按 UTC 处理时间，API 的时间点用 ISO 格式，日期字段保留 `YYYY-MM-DD`。桌面显示按浏览器本地时间；HTTP 客户端发送 `X-Timezone = Intl.DateTimeFormat().resolvedOptions().timeZone`。`timezoneOf()` 只接受有效 IANA 时区并规范化；登录成功时有效请求时区会写入用户记录。

具体入口有不同回落方式，不应把用户时区默认应用到所有 HTTP 请求：

| 场景                         | 当前源码的选择顺序                                                                              |
| ---------------------------- | ----------------------------------------------------------------------------------------------- |
| Excel 等请求内服务端渲染     | CLS 中有效 `X-Timezone` → 参数 `core.default_timezone` → `DEFAULT_TIMEZONE`（`Asia/Shanghai`）  |
| `Notifier` 的用户 id 收件人  | `iam_user.timezone` → 配置默认时区 → `Asia/Shanghai`；语言取收件人 `locale`，不取发送者请求语言 |
| `Notifier` 的直接邮箱/手机号 | 请求 CLS 时区 → 配置默认时区 → `Asia/Shanghai`；语言取 `currentLocale()`                        |
| 微信订阅消息                 | 接收人的已存时区 → 配置默认时区 → `Asia/Shanghai`                                               |

`currentTimezone(params, preferred)` 只处理传入优先值与默认参数；`Notifier` 显式传 `null` 计算用户通知的默认值，避免发送者时区覆盖接收人。通知的 `{ datetime: iso }` 参数经 `formatInZone()` 格式化；日期范围快捷项由 `useDateRangeShortcuts()` 在点击时计算本地日界，语言标签随切换更新。

## TODO 与验收

生成配置给出双语默认标签，但自动派生的英文仍需校对；新增片段的两个语言文件必须同键。`__todo.json` 和 en-US 空白值都计入 `scripts/i18n-check.mjs` 的规则 4。正常检查输出计数，严格模式把非零计数判为失败：

```sh
pnpm i18n:check
I18N_TODO_STRICT=1 pnpm i18n:check
pnpm verify
```

清零应补齐、校对译文，并在确实完成后移除对应 TODO 条目；不要删整个 TODO 文件伪造完成。检查还验证双语文件与键一致、重复键、静态引用、业务源码中的中文字符串，以及种子显示名和通知模板的双语约定。动态拼接键不都能被正则发现，英文自然程度和运行时第三方文案仍需人工验收。

人工观察：在隔离项目新增一个双语项目片段，切换中英，检查页面、菜单、校验错误、第三方控件与 Excel；用两种账号语言接收同一通知，核对发送时语言和时区。
