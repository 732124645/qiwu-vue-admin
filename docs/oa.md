# OA 办公

办公申请使用现有工作流。桌面“OA 办公”提供请假、出差、报销、用印、通用申请入口；我的申请、待办、已办和抄送沿用审批中心，不另存一份审批状态。手机端可阅读完整申请和附件并办理任务。

## 五类申请

| 类型 | 主要内容                                           | 审批后的业务结果                                             |
| ---- | -------------------------------------------------- | ------------------------------------------------------------ |
| 请假 | 类型、起止时刻、申报天数、事由、附件               | 回写原有请假单状态，保留旧数据和流程关联                     |
| 出差 | 目的地、起止时刻、事由、可选预计费用、附件         | 回写出差单状态；本人已批准出差可供报销引用                   |
| 报销 | 事由、费用日期和类别、逐项金额及附件、可选出差引用 | 回写主单状态，明细随申请同事务保存和编辑；批准不表示已经付款 |
| 用印 | 印章类型、文件名称、用途、份数、期望日期、附件     | 标记申请获批；不表示已经盖章                                 |
| 通用 | 已发布动态表单的字段和附件                         | 保存既有流程实例及表单快照                                   |

请假天数是申请人申报值，起止时间必须有效、结束晚于开始。系统没有按排班、节假日或年假余额自动核算天数。报销仅支持人民币，金额使用十进制文本，服务端以整数分计算，不能信任客户端合计。用印不连接实体印章或电子签章服务。

固定申请的保存、流程启动和初始状态回写在同一事务里。附件绑定、报销明细或流程启动失败时，不留下半张申请。流程通过、驳回、取消和管理终止时，业务状态随同一次审批事务更新，回写失败则流程动作一起回滚。

## 发起、退回和并发

首次安装只为缺失的出差、报销、用印和通用四个新增办公模型创建安全的默认发布版本：本租户的保护管理员角色办理，无可用审批人时拒绝发起，自审仍需本人明确处理。管理员已修改、停用、删除或发布的模型不会被初始化覆盖。请假沿用原来的示例流程和已发布配置，其中原示例的无人自动通过、自审跳过设置继续保留；新增四个模型的安全默认不会自动覆盖这些旧设置。部署后应在流程管理核对本组织的发起范围和办理人，再开展实际业务。

发起人自选节点由流程 `start-info` 指明，服务端核验所选人员。模型、表单、发布快照和节点行为见[工作流](bpm.md)。固定申请继续使用 custom handler，通用申请使用 dynamic 表单。

固定申请只允许本人编辑未发起草稿，或本人正在持有退回到发起节点的任务。退回时实例仍是运行态，不能只凭单据状态判断可编辑。已批准申请只读。其他人不能借编辑接口修改金额、事由或附件。

办理和业务编辑使用相同的实例优先取锁顺序；并发操作只有一个成功，冲突返回 409。页面刷新当前任务后再由使用者决定下一步，不自动重放审批。重复提交按钮处于等待状态时禁用，后端也有短时幂等检查；不能把网络重试当作新的申请意图。

## 谁能看见单据和附件

业务详情沿用工作流的发起人、当前或历史办理人、抄送人及具有数据范围的管理访问规则。知道单据或实例编号不构成授权。其他租户或不可见数据返回 404；管理员查询权限不能用来冒充当前办理人。

固定申请附件使用私有 `oa.attachment` 标签，动态表单附件使用 `wf.attachment` 标签。创建时核验本租户、上传者、文件占用和数量，绑定与业务提交同事务。单据移除的附件引用不能借旧绑定重新加入；报销主单和全部明细合并后最多 10 个有效附件。

上传者身份、root 或全局文件管理权限本身不提供业务附件访问权。全局文件目录和导出不列出这些私有标签，已绑定的业务文件不能经全局删除入口移除。动态表单隐藏字段中的附件不从元信息或下载接口泄露。

移动端通过鉴权元信息和固定同源内容接口读取文件，内容大小上限为 20 MiB。系统令牌不会发往对象存储重定向地址。附件恢复或决策信息加载失败时，手机端阻止业务决定并说明原因；不会提供空白信息供盲批。文件格式和预览能力仍取决于实际设备。

## 通知和移动端

待办、办理结果、退回、抄送、撤销和催办复用既有站内信、邮件模板与事务 outbox。业务事务提交后才发送；回滚不发通知，发送失败可重试，重试不重复制造业务事件。没有邮箱时沿用 skipped 记录；配置 SMTP 和真实邮件投递需由部署方验证。

手机端的待办、已办、申请和抄送与桌面共用接口。请假、出差、报销和用印展示完整只读决策信息；通用申请继续按当前节点字段权限渲染。既有手机请假发起、退回编辑和动态表单发起继续保留；新增出差、报销、用印的手机发起与编辑不在当前范围。原生打卡与审批分开，见[考勤](attendance.md)。

## 接入和验收

申请接口分别为 `/api/biz/leaves`、`/api/oa/trips`、`/api/oa/expense-claims`、`/api/oa/seal-requests`，通用申请和全部审批动作沿用 `/api/wf/*`。创建及编辑接口仍检查各模块权限；组织范围、套餐、租户和文件授权都在服务端执行。

新增办公业务应复用现有提交服务和 `WfBusinessHandler`，不能在控制器或助手中直接拼 SQL 改审批状态。金额、时间、附件和业务归属放在共享契约与服务端共同校验，handler 的回写必须接受既有事务管理器。开发细节见[项目接入](codegen.md)和[工作流](bpm.md)。

部署验收至少包含五类申请的发起、办理、回写，退回后修改重提，附件越权与撤销，双租户隔离，手机端完整详情及多端冲突。H5 自动化、App/小程序构建、设备上的登录、文件预览与审批是不同证据，应分别记录。

会议室、任务协同、用品资产、车辆、完整人事、合同公文、支付和电子签章需要独立业务设计；这些能力不因存在通用审批而自动具备。考勤也不依赖钉钉，外部打卡机接入属于可选集成。
