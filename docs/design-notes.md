# 设计说明

English summary: Qiwu separates framework, platform, workflow and project code. Shared schemas define validation and API contracts; Redis-backed opaque sessions, permission checks and scoped database access protect requests. This document describes the reusable design and links to detailed guides.

本文说明栖梧管理后台的公共设计约定，供业务扩展、代码注释与集成文档引用。

<a id="layering"></a>

## 分层与项目扩展

`core` 提供横切能力，`platform` 是平台模块，`workflow` 是流程模块，项目领域放业务代码。lint 与架构检查强制三条依赖规则：

- `core` 从不导入任何模块；
- `platform` 从不导入 `workflow` 或项目领域；
- `workflow` 从不导入项目领域。

项目领域可以使用以上各层。前后端共享 schema、类型与权限常量放在 `@qiwu/shared`。

项目代码放在 `modules/<领域>/<业务>`、`views/<领域>/<业务>`、`api/<领域>/` 与 shared 的领域目录，通过 `ProjectModule` 和项目种子注册。领域取表名第一段；包作用域保持 `@qiwu/*`。详见[代码生成指南](codegen.md)。

<a id="api-envelope"></a>

## API 与响应信封

资源路由使用 `/api/<领域>/<复数-kebab-case>`。成功响应为 `{ code: 0, msg, data }`，分页的 data 为 `{ items, total }`；失败响应携带业务码、已翻译的 msg 和 traceId，校验失败可附字段 errors。HTTP 状态表达真实语义：400 校验失败、401 未认证、403 无权限、404 不存在或超出数据范围、409 冲突、422 业务拒绝、429 限流或重复提交。

分页使用共享 `pageQuery`，排序字段须在白名单内。数据库会话与时间存储使用 UTC，API 时间为 ISO-8601，界面按本地时区显示；请求追踪号贯穿日志与审计。

<a id="auth-sessions"></a>

## 认证与会话

访问令牌与刷新令牌是不透明随机值，服务端以哈希和 Redis 会话验证身份。控制台 access 保存在内存，通过 Bearer 头发送；refresh 放在 HttpOnly、SameSite=Strict、限定 Path 的 cookie 中，刷新接口检查 Origin；设置该 cookie 的密码登录与短信登录拒绝外站 Origin（含 `null`），防止别的网站用表单把自己的会话种进来（登录 CSRF）。刷新轮换并检测重用，滑动续期不能越过会话绝对上限。保持登录控制 cookie 的持久性。

控制台、移动端与第三方 OAuth 客户端隔离，第三方令牌只进入显式开放的协议接口。改密、停用、删除与强退通过统一撤销服务清理凭据和连接；必须改密或密码过期时由服务端限制可访问端点。详见[安全基线](security.md)与[OAuth2](oauth2.md)。

<a id="permissions"></a>

## 权限与授权

权限码使用 `<domain>.<resource>.<verb>`，由各模块的 `xxxPerms` 导出，前后端同源。服务端使用 `@RequirePerm` 检查任一或全部权限，前端通过 `v-perm` 与 `usePerm` 显示操作入口。菜单隐藏不代替服务端授权。

权限来源为用户启用角色所关联的启用菜单的权限码并集；权限版本变化后，会话重新加载权限及部门范围。非超级管理员只能授予自己拥有的权限与数据范围，不能授予 root。重置他人密码或修改他人手机号等于拿到该账号，按授予该用户当前持有的全部角色（停用的也算）判断，超出调用者能授予的范围即回 403 `B1001`（文案 `takeover_exceeds_own`）；租户管理员持有其租户可用的全部权限点，只核对它持有的与平台专属的权限点（停用或套餐外菜单的权限点不计），其他管理员按其能否分配这些角色判断。移动部门把子树放到新的上级部门之下，那里持部门子树范围角色的用户从此看得到它，同样按授予判断；移动单个用户不改变任何角色覆盖的部门集合，只核对随用户移动的相对范围角色。内置 root 按角色代码及内置标志识别，不依赖固定数据库 id。

<a id="data-scope"></a>

## 数据范围与引用

数据范围包括全部、指定部门、本部门、部门子树与本人记录。带范围的实体通过 `scopedQb` 查询；写操作先在事务内用 `lockScopedIds` 锁定可见行，批量中任一 id 不存在或越界时整体返回 404。新增与编辑还需检查可写部门及属主。

软删除唯一性使用未映射的 `alive` 生成列；引用登记处理存活检查、限制删除与级联。规则链只管部门与本人范围；租户条件不在规则链里，由 ORM 层统一追加（见[多租户](#tenancy)）。详见[数据权限](data-scope.md)与[多租户指南](multi-tenancy.md)。

范围条件只在 ORM 路径上自动加上；手写 SQL 不经过 `scopedQb`，项目代码容易漏写。不对原始 SQL 做自动改写：解析任意 SQL 再插入条件，要为子查询、联表、UNION 各自找对位置，改错了就是悄悄多给数据或误伤查询，也难以评审。改为提供 `dataScopeSql`，它与 `scopedQb` 的默认规则链共用同一份范围计算（只是渲染成 `?` 占位），由写 SQL 的人显式拼入；不代表调用者读数据的系统查询用 `qw:no-data-scope <理由>` 显式豁免；架构检查 `data-scope-sql` 要求读带范围实体表的原始 SQL 字面量二者必居其一：是把范围直接写成 `${scope.sql}` 插进语句的模板字面量且所在函数自身调用了 `dataScopeSql`，或带标记；QueryBuilder 用表名字符串读这些表同样要标记。它是基于字面量的启发式检查，多个字面量拼成的 SQL、变量里的表名仍靠评审发现。用法见[数据权限](data-scope.md#手写-sql)。

<a id="tenancy"></a>

## 多租户

租户上下文放在 CLS：`tenantId` 是数据租户，`allTenants` 表示跨全部租户，`actorTenantId` 是操作者本人的租户。只经 `core/context/tenant.ts` 的 `withTenant`、`allTenants` 进入，嵌套运行结束后恢复外层的值；`tenantId()` 读不到时抛 `TenantContextMissing`，只有生产环境且多租户开关关闭时回落到默认租户并记错误日志。每个入口（HTTP 请求、Socket、调度、外部回调）先清空这三个键再写入，不继承外层或 `listen()` 时的上下文；调度处理器、回调按需自己选 `withTenant` 或 `allTenants`，业务代码里的每处调用都写明理由。

数据层自动加租户条件（`core/db/tenant-filter.ts`）：TypeORM 为租户表生成的每个 WHERE（查询、计数、子查询、更新、删除、逻辑删除，含不带 WHERE 的清空；`FROM` 列表里的每张租户表）与每个 join 都追加 `<别名>.tenant_id = <当前租户>`，原条件先整体加括号再拼接，避免原条件里的顶层 OR 绕过租户条件。条件在生成 SQL 时按当时的租户上下文加上；回调里用 `subQuery()…getQuery()` 写的子查询在构建时就已生成，所以查询要在执行它的上下文里构建。多对多关系不在覆盖范围内：TypeORM 自己拼中间表的 join 与写入，带不上租户条件，所以涉及租户表的 `@ManyToMany` 会让服务拒绝启动，关联表用 `core/db/links.ts` 或映射成实体。租户表不支持 ORM upsert（`orUpdate`、`repo.upsert`：`ON DUPLICATE KEY UPDATE` 没有 WHERE，会改到别的租户的冲突行），先按键读，再更新或插入；也不支持 `clear()`（TRUNCATE 会清空所有租户），用 QueryBuilder 删除。租户表按两路识别、取并集：实体用 `@TenantColumn()` 映射了 `tenant_id`，或表名在启动时从库结构读出的租户表清单里（没有实体的关联表与按表名的 join 靠它）；平台表不加条件：`core/db/tenant-tables.ts` 的 `PLATFORM_TABLES` 由模板自己的登记与项目的 `db/project-tables.ts`（`PROJECT_PLATFORM_TABLES`）合并而成，全局唯一键 `GLOBAL_UNIQUE` 同样合并 `PROJECT_GLOBAL_UNIQUE`；项目的表只登记在项目文件里，模板升级不会改它。root 与 `@SkipDataScope()` 只跳过部门规则，跳不过租户条件。写入订阅者用上下文租户覆盖插入值，生成 INSERT 时再覆盖一次（关掉监听器也一样），更新时不改 `tenant_id`。这套机制依赖 TypeORM 的内部结构，所以 `typeorm` 锁定精确版本，并由契约测试与启动自检兜住：自检生成的 SQL 里缺租户条件、或租户表清单为空时，服务拒绝启动。原始 SQL 不经过 ORM，须自己写租户条件。

默认租户 `id=1` 拥有开关打开之前的全部数据，同时是平台运营方：平台表（`PLATFORM_TABLES`：菜单、字典、参数、任务、存储配置、OAuth 客户端、通知模板与渠道、API 访问与错误日志、租户、租户域名与套餐）由它维护、全部租户共用。启用与运维见[多租户指南](multi-tenancy.md)。

开关 `APP_MULTI_TENANT` 只用环境变量、启动时读取、默认关闭。关闭时每个 HTTP 请求预置默认租户；打开时不预置，租户只来自登录前解析、会话（AuthGuard、刷新）或公开路由处理的资源行，漏写来源的公开路由一碰租户表就是 500，不会落到默认租户。会话记下用户本人的租户（取自用户行，签发时断言存在）；缺这个字段的旧会话先按用户行重载，从不当作默认租户。租户可用 = 已启用 ∧ 未到期 ∧（开关打开 ∨ 默认租户）：每次使用会话只看开关与会话里记下的租户到期时间，完整判定在加载用户时（签发、权限版本变化后的重载、授权码兑换）；不可用时吊销会话、回 401 `A1042`，Socket 收到带原因的 `session:kicked`。会话的绝对期限不超过租户的到期时间，空闲 Socket 由每分钟的复查按同样的规则重载。后台任务的扫描查询只取可用租户的行（事后跳过会让它们永远排在队头）。停用租户时 `SessionRevoker.revokeTenant` 结束它的全部会话。开关打开且请求的主机名绑定了租户时，别的租户的令牌回 401 但不吊销，刷新同样拒绝。租户表的 `tenant_id` 与 `aud_action_log.actor_tenant_id` 由迁移加上 `DEFAULT 1`（与旧代码兼容，开关关闭的安装一直保留）；`db/tenancy-harden.ts` 只改元数据地去掉这些默认值，之后漏写 `tenant_id` 的插入报 1364（可空的登录日志同样如此；关闭严格模式的库里漏写的行落到不存在的 0 号租户或 NULL，谁都看不到），而不是落到默认租户。开关打开时 `db:migrate` 迁移后自动执行它，从已有库升级、同一次运行刚执行租户迁移时不执行（旧版本还在服务，它的插入不写 `tenant_id`）；`db:reset` 与测试库每次重置都执行。此后的迁移新建租户表时 `tenant_id` 不带默认值，迁移里往租户表 INSERT 时显式写 `tenant_id`（加固过的库没有默认值可落）。生产环境打开开关、仍有带默认值的租户列时拒绝启动；关闭开关时仍有启用的非默认租户，启动日志会警告，可用 `node dist/db/tenant-disable.js <编码…>` 停用。

登录前的租户由 `core/auth/login-tenant.ts` 的 `resolveLoginTenant` 解析，它是会话出现之前唯一写入请求上下文租户的地方（模块里的入口调用它，不自己写）：开关关闭时恒为默认租户，请求体里的编码与主机名都不看；打开时先按 `req.hostname` 精确匹配租户绑定的域名，否则取请求体里的租户编码，留空即默认租户；编码与主机名的租户不一致回 400 `A1041`。解析结果只决定去哪个租户核对凭据，身份取自核对通过的用户行。编码不存在、租户停用或到期都是同一个“未解析”：密码登录照样对假哈希做一次 bcrypt、回同样的 `bad_credentials`、照常累加失败计数，存在与不存在的编码响应完全相同，不能借此枚举编码；登录日志里编码不存在的一行 `tenant_id` 为空（哪个租户都看不到），停用或到期的记到该租户；公开路由读不到租户时不写操作日志。登录失败计数按规范化后的输入编码区分：`default` 沿用原来的 `p:`、`u:` 键，其他编码（不存在的也一样）用自己的 `tp:{编码}:`、`tu:{编码}:` 段，不在 `p:`、`u:` 后面再加一段（解锁按 `p:{用户名}:*` 扫描，与用户名同名的编码会被扫到）；解锁只作用于调用者数据租户的计数。`GET /api/auth/tenancy` 只告诉登录页开关状态与当前主机名绑定的租户，不提供按编码查名称的接口。

Redis 命名空间各自声明租户维度（`core/redis/cache-namespaces.ts`）：用租户内才唯一的自然键（用户名、手机号、编码、名称）建键的是 `tenant`，`redisKey` 与 `keyPattern` 自动在命名空间后面加 `t:{租户}:` 段，上下文里没有租户或处在 `allTenants` 里直接抛错；只用全局唯一值（会话 ID、令牌或内容哈希、全局数字 ID、AppID）建键、或有意跨租户共用的是 `global-id`（登录失败计数自带编码段，按手机号与 IP 的短信限额保护的是机主）；字典、参数、任务锁与触发记录、限流是 `platform`。缓存列表对 root 列出全部租户的键；其他人只在开关关闭时到得了这一页，看不到别的租户的键（`tenant` 命名空间只到本租户的段，登录失败计数去掉 `tp:`、`tu:`），按键查看与删除同样回 404。

短信验证码、小程序登录与 OAuth2 授权码同样按租户。短信发码、短信登录、短信重置密码与小程序绑定都先经 `resolveLoginTenant` 解析租户：验证码在解析出的租户里签发、消费与作废，同一手机号在两个租户各有用户时互不影响，登录与重置只找该租户里持有这个手机号的用户；解析不出租户时与手机号不存在走同一条路径（同样的响应，同样计入校验次数，不发码）。按号码的冷却、每日上限与校验次数仍跨租户共享，保护的是机主；已登录用户绑定手机号的验证码属于会话的租户。小程序静默登录不需要租户编码：一个微信身份只绑定一个租户的一个账号，按绑定行找到用户，在用户所在的租户里签发会话（该租户须可用）。绑定票据记下签发它的请求的主机名所绑定的租户，这样的票据只能在该租户绑定；主机名没有绑定租户时（主域名、App、小程序），票据在绑定请求解析出的租户里使用。OAuth2 授权码记下批准它的会话本人的租户，兑换在该租户里进行，用户不属于它即按无效授权码处理；`client_credentials` 会话属于默认租户，只用于平台自身的系统集成。

root 只认默认租户：内置 root 角色的行与持有它的用户行都要在默认租户，两边都查，别处的关联校验即使漏掉也造不出 root，所以 root 就是平台超管；它的在线会话列表与踢人也只到数据租户，别的租户的会话回 404。各租户的管理员是内置角色 `tenant_admin`：不写菜单授权行，权限取所在租户套餐内对租户开放的菜单（平台专属菜单上的权限点一律不给），侧栏菜单同样如此，不是 root。它在本租户内按 root 对待数据范围的授权规则：可以把角色设为全部数据范围、分配这样的角色与 `tenant_admin` 本身；只能授予自己持有的权限点照旧，也只能分配本租户的角色（别的租户的回 404）。内置 `tenant_admin` 角色行与 root 角色一样不可停用、删除，也不能改数据范围或菜单授权。非 root 的菜单编辑让其他租户的任何角色多出权限点即按越权授予拒绝（按角色的菜单授权计算，不先按套餐与平台菜单剔除，`tenant_admin` 按全部对租户开放的菜单计算，所以只会多拒绝），本租户的角色多出的权限点照常要求编辑者持有并按数据范围判定。受保护用户是 root 持有者、租户所有者（`iam_tenant.owner_user_id`，开通时建的管理员）与 `tenant_admin` 持有者：改他们的密码、联系方式、部门、角色或踢他们的会话，root 用户与所有者只有 root 能做，其他 `tenant_admin` 持有者 root 或 `tenant_admin` 持有者能做；root 用户与所有者谁都不能停用或删除，其他持有者只有 root 或 `tenant_admin` 持有者能。违反时回 422 `user_protected`。所有者在用户管理与在线会话里也不能操作自己（改自己的用户资料、踢自己的其他会话），这些由 root 处理。默认租户没有所有者与 `tenant_admin`，判定与单租户时一致。

注册只服务默认租户：开关打开时，解析出其他租户或解析不出租户（编码不存在、停用、到期）一律与注册关闭时相同，存在与不存在的编码响应完全相同。所有建用户的入口（后台新建、Excel 导入、注册、开通租户）都在同一事务里先 `SELECT … FROM iam_tenant WHERE id = ? FOR UPDATE` 锁住租户行，再数该租户的存活用户，加上本次新增超出 `user_quota` 即回 409 `B1013`，`user_quota` 为 `NULL` 表示不限（`modules/platform/iam/tenant/tenant-quota.ts`）。加锁必须是事务里的第一条语句：计数是普通读，读的是事务的一致性快照，而快照从事务里第一次普通读开始；先读了别的再加锁，计数看到的是加锁之前的旧快照，两个并发的新建会同时通过。

开通租户（`TenantProvisioner`）在一个事务里完成，任一步失败整体回滚：插入租户行；运行租户级种子 `TENANT_SEEDS`（以租户名命名的根部门、内置 `tenant_admin` 角色、流程模板、审批人为本租户 `tenant_admin` 角色的请假流程，再是项目的 `PROJECT_TENANT_SEEDS`）；在用户配额内建管理员（持 `tenant_admin`、在根部门、首次登录须改密）并记为所有者。每个租户有自己的初始密码：开通时按密码策略随机生成，租户行上只存 SecretBox 密文，明文只在开通结果里返回一次，也是管理员的首个密码；该租户后台新建或导入用户而不填密码时用它，默认租户仍用参数 `iam.user.initial_password`。共用一个值时，一个租户的管理员能用它登录另一个租户刚建、还没改密码的用户。`db:seed` 的 `SEEDS.tenant` 对每个已有的非默认租户（含停用、到期的）重跑同一清单，补齐新版本加的租户级种子；这些种子只插入缺少的行，不建管理员，不复活租户删掉的行。默认租户的人员与演示数据只来自原有种子，租户级种子从不在默认租户运行。

已知上限：主机名到租户的查找有 60 秒进程内缓存，改绑域名最多 60 秒后生效；`revokeTenant` 扫描全部在线会话，会话量很大时再改为每租户一个有序集合；开关从打开改为关闭后，其他租户留下的按手机号或 IP 计数的键（短信限额、登录失败的 `ip:`）在缓存列表里照常列出，它们都带过期时间，最长约两天；短信验证码的全站每日上限由所有租户共用，一个租户能把它用完；短信入口里“解析不出租户”与“手机号不存在”只在响应体与状态码上相同，耗时相差一次数据库往返；调高 `iam.password_min_length` 后，已开通租户的初始密码可能不再符合密码策略，这时该租户后台新建或导入用户必须填写密码，或在租户管理里重置该租户的初始密码（按当前策略重新生成）。

平台页面有三道检查：菜单的 `platform_only` 按祖先继承（shared 的 `PLATFORM_ONLY_ROUTES` 列出这些页面）；非默认租户的会话加载时剔除平台权限点（出现在任一平台菜单上的权限串）；控制器闸门 `@PlatformOnly()` 要求操作者本人在默认租户（`'root'` 变体只放行平台 root）。平台接口一律在操作者本人的租户里运行。含其他租户数据的平台页（API 访问日志、API 错误日志、缓存列表）开关打开时只限平台 root；两张 API 日志表对非 root 无论开关如何只返回匿名与默认租户的行。API 日志的 `tenant_id`：已登录的请求写数据租户，匿名请求、公开的登录类请求与 `client_credentials` 会话写 NULL。登录日志的“未解析租户”筛选只用于平台 root 的列表与导出，这些行的详情与删除仍回 404。租户与套餐两页不含其他租户的业务数据，所以用普通权限点，可以授予默认租户里的平台人员。

租户管理（`modules/platform/iam/tenant/`）。绑定域名的整组替换由租户服务自己改写 `iam_tenant_domain`：去掉的按 `tenant_id` 与域名逻辑删除，即刻可以绑给别的租户；新加的用普通 INSERT，撞上别的租户的存活行时 1062 转成 409 `duplicate`（不透露占用者）；不复用 `core/db/links.ts`，它靠 `ON DUPLICATE KEY UPDATE` 复活旧行，用在这里，绑定别的租户仍存活的域名会变成对那一行的空更新，请求成功却没绑上。平台自己的主机名（当前请求的主机名与 `CORS_ORIGIN` 里的主机名）不能绑定（422 `B1016`）：否则主域名上的登录全部解析到该租户，平台人员的令牌在主域名上被主机名闸门回 401，平台被锁死，只能改库恢复。停用在提交后 `revokeTenant` 并 `bumpAll`；换套餐与改到期时间在提交后 `bumpAll`：套餐只在身份加载时强制，而加载只在权限版本变化时重跑，漏了它，降级的租户在会话有效期内仍能用已移除的功能；重载时会话的期限封顶到新的到期时间，新的到期时间不晚于当前时间按停用处理。默认租户不能停用、设到期时间或套餐，编码不能改，也没有租户初始密码（422 `B1015`）。租户从不删除，编码因此永不复用；全局唯一的值逐项登记释放方式（`GLOBAL_UNIQUE`），小程序微信号在停用、到期的租户里由持进入权限的平台人员进入后删除用户或重置其密码释放。

套餐只在身份加载时强制（`IamUserLookup.load` 与 `menus()`）：非默认租户的权限 = 角色授权 ∩ 套餐 − 平台权限点，`tenant_admin` 的权限 = 套餐的全部权限点；`PermGuard` 不改，会话里的权限已经过滤过。没有套餐、或套餐已停用、删除的非默认租户功能集为空，不当作不受限：漏设套餐的租户静默拿到全部租户功能，比什么都不能用危险得多。角色授权树与 `setMenus` 的可编辑范围收窄到“套餐 − 平台菜单”，范围外已有的授权行原样保留（整体替换会删掉它们），所以套餐缩小再放大后原授权恢复。防越权授予的判定（`GrantPolicy.perms()`）仍计入套餐外与平台菜单上的这些旧授权：套餐缩小或菜单改为平台专属后，带这类旧授权的角色只有持有这些权限点的人能分配或重新启用，套餐放大后恢复。只要求登录、属于某个功能组的接口用 `@RequireFeature('<菜单分组>')`，不在会话的功能集里回 404；不用 `@RequirePerm`，它会让默认租户里没有该权限点、今天却能用这些接口的用户失去访问，违反开关关闭时零变化。`GET /api/auth/me` 的 `features` 列出会话可用的顶层分组，只在开关打开时带，客户端缺省按全部可用。套餐与菜单的级联登记在引用注册表里：删除菜单时同一事务逻辑删除套餐里的行。

平台人员进入租户写在服务端会话里（`actingTenantId`、`actingUntil`，最多 2 小时），不靠请求头，不冒充目标租户的用户，userId 仍是本人。进入要求可授予的权限点 `iam.tenant.enter`（root 隐含）、本人在默认租户与网页后台的会话；目标租户停用或到期也能进入。`AuthGuard` 在 `load` 之后把数据租户设为目标租户，`actorTenantId` 仍是本人租户；`@HomeTenant()` 的个人类路由（`/auth/me`、个人资料、改密、表格偏好、我的站内信、公告、我的待办与我的流程）与全部 `@PlatformOnly()` 路由仍按本人租户运行，否则 root 在目标租户里打开字典、参数、模板测试发送等平台页，操作日志、发送记录与参数校验都会落到目标租户，目标租户的管理员能读到平台配置的请求参数。本次请求的权限去掉平台权限点（root 仍是 `*`），所以非 root 在目标租户里用不了平台页，也不能再进入别的租户；`@RequireFeature` 对进入状态恒通过，不按目标租户的套餐收窄。到期、开关关闭（进入状态存在 Redis 会话里，重启后还在）或本人不再持有 `iam.tenant.enter` 时，下一次请求先清掉进入状态、记 `leave`，按本人租户继续；这条判定读本人的权限（做差集之前），`iam.tenant.enter` 本身是平台权限点，按差集之后判定，任何一次无关的权限重载都会把人踢出。`leave` 不要求权限点，否则进入期间失去平台权限点的人就困在目标租户里。数据范围照本人角色计算，部门规则引用的是默认租户的部门，在目标租户里只有全部数据范围看得到数据。进入者不是目标租户的 `tenant_admin`，受保护用户照旧只有 root 能改。socket 不加入目标租户的房间。

进入的审计：`enter`、`leave` 两行写在默认租户（`biz_id` 为目标租户），被审计的租户删不到；默认租户侧的删除与清空同样排除这两类行，只由保留期任务 `audit.purge` 清理，按 id 删除回 404。进入期间租户侧接口的操作日志 `tenant_id` 为目标租户、`actor_tenant_id` 为默认租户，每行记着操作者本人；租户侧的列表、详情与导出遮蔽这些行的 IP、地点、UA 与部门快照（写法同演示模式的遮蔽），只显示“平台人员”与用户名，删除与清空排除它们。完整的来源信息在平台表 `aud_http_trace`：进入期间的请求（含 GET）与 `enter`、`leave` 两个请求本身一律写入，不受访问日志参数与排除路径影响。会话结束时（退出登录、踢出、改密、停用）`SessionRevoker` 为带进入状态的会话补写 `leave`；会话自然过期没有事件，以 `enter` 记下的 `actingUntil` 与会话到期两者较早者为结束。

多标签页防误写：网页每个请求带 `X-Tenant-Expect`（页面加载时的 `/me.tenant.id`，即会话的进入租户或本人租户）；服务端对网页后台的会话一律与会话当前的数据租户比对，与路由是否按本人租户运行无关（否则进入期间每个平台页与 `/auth/me` 都会冲突），不符回 409 `A1040`，前端整页重载。这个头只能让请求失败，不能选择租户；没带不检查，移动端与第三方不受影响。

品牌（名称、logo）存在租户行上。logo 一律是默认租户里的公开 `cover` 对象：平台人员在租户表单里上传（租户管理接口在本人租户里运行），保存时在默认租户里校验它存活、公开且是 `cover`，并绑定引用，清理任务不删；读取一律在默认租户里按 id 取公开地址。登录前 `GET /api/auth/tenancy` 只在主机名绑定了租户时返回它的品牌，不提供按编码查品牌的接口（否则可以探测编码）；登录后从 `/me.tenant` 取。favicon、`index.html` 的静态标题与 App 图标保持统一。

进入租户与套餐的已知上限：套餐的变更、启停与租户换套餐都用全局的 `bumpAll`，每次让全部会话重载一次权限，租户多了以后改为每租户一个权限计数；进入期间每个请求多读一次平台权限点清单（进入的人少、时间短）；平台人员看其他租户的操作与登录日志只能先进入该租户，没有平台跨租户的日志视图（登录日志里未解析出租户的行除外，平台 root 有只读筛选）；一个微信号只能绑定一个租户里的账号；在主域名上用租户编码登录时，同一浏览器同一时间只登录一个租户（刷新令牌的 cookie 按主机名只有一个）；换 logo 后旧对象仍保持绑定（清理任务不删），换回旧 logo 要重新上传；进入期间换自己的头像或上传租户 logo 会失败（上传的对象落在目标租户），先退出再做；进入状态存在会话 JSON 里，与正在重载权限的请求并发时可能被旧快照写回，`aud_http_trace` 仍逐条记录这些请求，最长持续到 `actingUntil`。

<a id="wxoa"></a>

## 微信公众号模块

公众号功能分两组：账号、回调、菜单、粉丝、素材、消息、自动回复、模板与二维码；图文草稿、发表、群发、统计、留言、订阅通知。模块由启动开关 `APP_WXOA` 决定是否加载（默认关闭）：关闭时 `WxoaModule` 不进模块列表，路由（含回调）不存在、任务处理器不注册（调度器不排定时处理器未注册的任务），菜单按 `core/auth/menu-features.ts` 的开关表从侧栏与授权树隐去，与租户管理页随多租户开关的做法相同；表照常由迁移创建。管理接口统一挂在 `/api/wxoa`，控制器使用 `wxoa` Swagger 标签。微信上游始终由 `WxoaGateway` 调用，演示模式拒绝出站；回调和异步回执统一经过 `WxoaInboundHub`，在响应或回执处理时进入账号所属租户。

草稿正文走共享富文本清洗器。同步草稿时只把当前租户、当前公众号账号的 `richtext` 公开 jpg/png 对象上传到微信；服务端不按用户提供的 URL 访问外网，不从路径猜对象键，所有正文和上游响应都在大小上限内处理。远程微信图片只允许 `mmbiz.qpic.cn` 与 `mmbiz.qlogo.cn`，留言按纯文本渲染。发布和群发在本地保留任务状态，使用上游回执排重；群发任务使用 `clientmsgid` 幂等，重复请求不会创建第二个发送任务。

草稿、发表、群发和内联图片表与其余公众号表一样是租户表，实体映射 `@TenantColumn()`，每一张表同时有 `deleted_at` 逻辑删除列。账号、标签、粉丝、草稿和素材的引用必须属于当前账号与当前租户；请求中的 `accountId` 只用于定位资源，不是租户选择器。ORM 自动追加租户条件，原生 SQL 必须显式写 `tenant_id = ? AND deleted_at IS NULL`。跨租户资源与已删除资源使用相同的 `404` 口径，避免泄露资源存在性。公开回调先在 `allTenants` 下按回调 key 找账号，账号所属租户不可用（停用、到期、套餐不覆盖公众号分组，或多租户开关关闭时的非默认租户）时按未知 key 处理，否则使用 `withTenant(account.tenantId)` 完成验签、落库和后续处理。`wxoa.fan.sync` 与 `wxoa.message.purge` 由调度器在无租户上下文里触发：先在 `allTenants` 下只取可用租户的账号或租户，再逐个 `withTenant`，一个租户失败只记日志。access_token 的缓存与进程内单飞都按账号 id（全局 id）存放，不按 AppID：同一 AppID 删除后由另一个账号（可能是另一个租户）重新接入时，拿不到旧账号的令牌，也不会并入它的在途请求。

已知上限：多租户开关打开时 `wxoa_account.app_id` 跨租户唯一（`GLOBAL_UNIQUE`，释放方式 `row-delete`），一个公众号只能接入一个租户；新建账号先用提交的 AppSecret 换一次令牌，证明添加者持有该公众号，避免一个租户抢先占用别人的 AppID。占用中的 AppID 只有删除账号才释放；停用或到期租户占用的 AppID，由持进入权限的平台人员进入该租户删除账号释放，平台的租户列表可按 AppID 查到占用的租户。

认证要求按微信能力提示：草稿、发表、群发、统计、留言和订阅通知以认证服务号为目标，测试只使用假网关；真实号权限、配额和字段差异需在真实账号上核对。订阅通知的用户授权（H5 JS-SDK 开放标签）不由后台模块代办。

<a id="audit"></a>

## 审计与追踪

实体审计订阅器从请求上下文填入创建人和更新人。每个非 GET 控制器方法声明 `@ActionLog` 或显式 `@SkipActionLog()`；登录日志、HTTP 访问记录与故障记录有各自入口。项目自定义动作在项目动作词种子中注册。

日志共用敏感字段脱敏与大小限制，追踪号连接请求、错误与审计记录。配置保留期（`audit.retention_days`，只有 root 能改）的清理任务物理删除过期记录；记录失败会写运行日志，审计不代替业务事务。

<a id="i18n"></a>

## 国际化

界面、后端消息、共享校验及字段标签同时提供 zh-CN 与 en-US。菜单和种子显示名使用翻译键；字典、参数等运行期内容可保存双语 JSON，并保留原文回落。界面切换语言时同步组件库、日期库与第三方组件，并向后端发送语言头。

校验消息使用 `validation.*`，字段标签使用 `field.<domain>.<prop>`。不要在业务源码硬写中文提示；详见[国际化指南](i18n.md)。

<a id="validation"></a>

## 校验与共享契约

Zod schema 放在 `@qiwu/shared`，同时生成类型、服务端请求校验、Swagger 描述与表单规则。输入校验由服务端最终执行，浏览器规则用于提前反馈；排序、标识符与动态表单行为均受白名单约束。

schema 注册字段领域，派生 schema 也需注册；校验问题转换为翻译键与参数。服务端不维护独立的 validation / field 文案副本，详见[校验选型](adr/003-validation.md)。

<a id="crud-kit"></a>

## CRUD 页面与对话框

列表使用 `QwTable` 与 columns 数组，通过 `#cell-<prop>` 和 `#actions` 扩展单元格与操作；`TableToolbar` 使用同一列配置，`table-id` 为 `<domain>.<biz>`，用户列偏好由 `useTablePrefs` 保存。

操作列只直接显示前几个按钮（页面设置里的“表格行内操作按钮数”，默认 2；单个表格用 `actions-visible` 覆盖），其余收进悬停（或键盘 Enter / 空格）展开的“更多”菜单，危险按钮（`type="danger"`）总排在最后；没有权限（`v-perm`）的按钮不占位。只拆分插槽里直接写的 `el-button`：包在其他组件里的按钮（如 `el-popconfirm` 的 `#reference`）、图标按钮和页面自带的下拉菜单保持原样留在行内，不计入按钮数；页面自带“更多”下拉时传 `:actions-visible="Infinity"`，避免出现两个“更多”。列宽按每行实际渲染出的操作内容测量（取最宽的一行，内容变化时重新测量），首帧先用按文字估算的宽度；显式的 `actions-width` 优先。

新增与编辑表单是接收可选 id、发出 done/cancel 的对话框内容组件，使用 `useCrudForm`，通过 `openDialog` 打开。提交期间按钮显示 loading 且禁用；创建接口另有短时幂等保护。详见[黄金样板](codegen-golden.md)。

<a id="codegen"></a>

## 代码生成

生成器从数据库元数据与配置输出单表、树与主子模块，包括服务端、shared、Web、权限、种子与测试。预览和下载不写工作区；工作区写入须显式启用并检查目标、覆盖和路径安全。生成器不复制其他后台模板实现。

模板里的值一律经 `<%= %>` 输出，它的转义函数只放行普通标记与 `str()`、`json()`、`comment()` 的结果；不转义的 `<%- %>` 只用于 `include('<字面路径>')`（架构检查 `ejs-lint`）。

黄金样板由配置重新渲染并逐字节比较，模板与样板应一起更新；项目菜单组和动作词通过项目种子重建。详见[代码生成指南](codegen.md)与[黄金样板](codegen-golden.md)。

<a id="workflow"></a>

## 流程与表单

树形与 BPMN 设计器共享树形运行引擎，画法与表单来源独立。发布形成版本快照；审批、分支、抄送与超时动作按结构化配置执行，拒绝脚本、表达式和监听器。BPMN 只支持可编译到树形模型的子集，并保留 bpmn.io 标志。

业务表单通过注册表接入，动态表单受双端 schema 白名单与字段访问控制；计算值由服务端重算。详见[流程接入](bpm.md)、[BPMN 设计器](workflow-bpmn.md)与[超时处理](workflow-timeout.md)。

<a id="storage"></a>

## 文件存储

本地与 S3 存储共用对象元数据、标签与属主检查。public 本体可由反向代理托管，private 文件通过鉴权 API 下载；上传检查大小、类型、魔数与路径，直传确认再次验证属主和对象。改变 S3 目标或访问密钥时必须重填 secret。

多实例本地存储要求共享卷，也可使用共同的 S3 配置；出站连接受地址与端口限制。详见[部署指南](deploy.md)与[安全基线](security.md)。

<a id="realtime"></a>

## 实时与通知

Socket.IO 握手验证会话，按用户与用户类型发送业务事件；事务相关通知在提交后推送。多实例使用 Redis 分片适配器，部署间以 Redis 库号和频道前缀隔离。

推送不持久化，也不支持连接状态恢复；可靠数据先落库，经 REST 补拉，客户端保留重连刷新与轮询。详见[实时推送](realtime.md)、[通知中心](notify.md)与[多实例部署](scale-out.md)。

<a id="queue"></a>

## 任务队列

后台任务用 BullMQ 跑在应用已有的 Redis 上，而不是另起 RabbitMQ、Kafka 之类的消息服务：模板的部署本来就必须有 Redis（会话、限流、推送适配器），再加一个服务就多一份安装、监控、备份和 ACL 配置，而队列要解决的问题（重试、延迟、并发消费、失败可查）BullMQ 都覆盖，吞吐也远超后台管理系统的需要。代价是 Redis 必须用 `noeviction` 且容量要算上排队的任务，并且只承诺至少一次执行，处理器须幂等。任务数据记下添加者的租户，处理时在该租户里执行，没有租户的任务拒绝执行。详见[任务队列](queue.md)。

<a id="security"></a>

## 安全默认值与验证码

默认要求认证，写操作检查权限、数据范围与日志；SQL 参数化，富文本清洗，出站连接防 SSRF，文件和 Excel 有内容及资源限制。秘密只进入忽略的 `.env.local` 或进程环境，不能放入 `VITE_*`；生产拒绝测试凭据标记。

SQL 只写一个字面量，值经 `?` 或 `:name` 占位作为参数传入（架构检查 `no-sql-concat`）；只有代码自己写定的标识符（别名、列名）可以拼进 SQL，在该行或上一行写 `// arch-allow: sql-concat <理由> tenant: <怎样留在租户内>`。源码不用 `eval`、`new Function` 与 `vm` 模块（架构检查 `no-eval`），数据用 `JSON.parse` 或代码里写定的处理函数表解析。

验证码模式为 off / image / slider，默认 slider；图形使用自绘字形，滑块使用 sharp 生成拼图。校验成功发出单次票据，绑定场景和 IP；跨 IP 的账号失败计数可强制验证码，即使普通模式关闭。验证码与限流、失败计数共同工作。详见[安全基线](security.md)与[环境准备](getting-started.md#2-空库账号与隔离)。

<a id="mobile"></a>

## 可选员工移动端

`mobile/` 是独立于根 pnpm workspace 的 uni-app Vue 3 员工客户端，复用 shared 契约与现有审批接口，面向小程序和 App，H5 用于调试。PC 管理端仍以桌面浏览器为目标。

PC 项目可按步骤删除 mobile；真机、外部消息与发布需要在目标环境核对，动态表单部分控件和附件仍有限制。详见[移动端指南](mobile.md)。
