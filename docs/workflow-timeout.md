# 审批超时自动处理说明

> BPMN 画法见 [workflow-bpmn.md](workflow-bpmn.md)。

## 配置

审批节点的"超时提醒"打开后（`timeout.hours` 办理时限，可选 `remindEvery` 重复提醒间隔），多一个"到期后"选项（`timeout.action`）：

| 到期后         | `action`     | 系统做什么                                                                                                                                       |
| -------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 仅提醒（缺省） | 不写         | 只提醒办理人（`wf.task.overdue`），与以前完全相同                                                                                                |
| 自动通过       | `autoPass`   | 以办理人的名义"通过"，`any`/`all`/`ordered` 规则照旧：`all` 的多个待办各自到期各自处理，`ordered` 的下一位从此刻起计时                           |
| 自动驳回       | `autoReject` | 以办理人的名义"驳回"，按本节点的"驳回后"：`finish` 结束实例并取消其它待办（含并行路径），`sendBack` 退回上一个走过的审批节点（见下文"不会循环"） |
| 转给上级       | `toManager`  | 把待办转给办理人的上级（见下文），新待办重新计时                                                                                                 |

- 逐个节点开启；未配置 `action` 的节点行为不变。树形设计器的节点抽屉与 BPMN 设计器的属性面板是同一个设置组件，两种模型都能用（BPMN 模型存在 `qw:Config` 里）。
- 到期时间仍是 `wf_task.due_at`（自然小时）。处理由每 5 分钟运行一次的定时任务 `wf.task.remind` 完成，**精度约 5 分钟**：到期后最迟约 5 分钟处理。不新增定时任务、表或列。
- 注意同名不同义：节点的"无人审批时"里的"转交流程管理员"（`whenNobody: 'toManager'`）指模型的流程管理员；这里的"转给上级"指办理人的上级。

## 处理哪些待办

只处理**审批人自己的**到期待办：状态为待办（`pending`）、不是子任务、`due_at` 已到、还没有被提醒或处理过（`reminded_at` 为空，每条只处理一次），并且从未委派或加签过。下列情形**只提醒**、不自动处理：

- 委派中、前加签挂起的任务（它们不是待办状态；恢复为待办后也只提醒）；
- 受托人与加签人的子任务；
- 处理过一次之后（含"无人可转只提醒"与"处理失败"）的后续提醒。

发起人的任务（被退回发起人）没有到期时间，不涉及。

## 转给上级：找谁

1. 办理人所在部门的负责人（只算启用的负责人）；负责人就是办理人本人时，取上级部门的负责人。
2. 这个人须**合格**：不是办理人；**本轮没有在该节点经手过**（同一轮的转交链上出现过的人都不算，包括正在该节点持有待办的人）；节点的"发起人即审批人时"不是"由发起人自己审批"（`self`）的话，也不能是发起人。
3. 找不到或不合格（没有部门、部门无负责人或负责人停用、上级部门负责人缺失、仍是本人、经手过、是发起人）→ 按模型"流程管理员"的**配置顺序**取第一位启用且合格的管理员（同样跳过发起人与本轮经手人）。
4. 再没有 → 不转交，只提醒办理人并记录（结果 `remindOnly`）。
5. `any`（一人通过即可）节点例外：上级或任一流程管理员已经在本节点持有待办时，直接只提醒，不再把别人卷进来（例如同部门两人同时到期，第一条转给负责人，第二条只提醒）。

新办理人再超时，按同一规则转给**他的**上级；每一跳都是本轮没经手过的人，所以转交链一定有终点、不会来回往复，最后停在"只提醒"。

## 不会循环

- 自动驳回选择退回目标时，**跳过本轮最新一次通过是"超时自动通过"的节点**；全部被跳过就退回发起人。发起人的待办没有到期时间，所以"A 自动通过、B 自动驳回退回 A"不会无限循环。
- **自动通过的审批不能撤回**（撤回接口返回 409，详情页也不显示"撤回"）。只提醒或处理失败之后由本人通过的审批照常可以撤回。

## 交接与撤回重新计时

节点配置了 `action` 时，以下新出现的待办按"现在 + 办理时限"重新计时，否则会沿用旧的到期时间、下一轮就被自动处理：

- 人工转办出来的新待办；
- 管理员在"任务管理"中改派的待办（只在待办状态时；顺签还没轮到的任务仍没有到期时间）；
- 审批人撤回审批后恢复的待办（`any` 节点里一并恢复的同伴也是）。

撤回不清空"已提醒/已处理"标记：之前已经记录过超时的任务撤回后只提醒、不再自动处理。未配置 `action` 的节点保持原样（到期时间不变）。

## 不静默：时间线与通知

- **时间线**：每次处理写一条系统（无操作人）的"超时处理"（`timeout`）事件，意见为 `seed.wf.timeout.*` 的文字，并写明是谁的待办，例如"张三 的待办：超时未处理，系统已自动通过"。转给谁、退回到哪个节点也在事件里。用户自己写的意见原样显示，不会被当成系统意见。
- **通知** `wf.task.timeout`（站内信 + 邮件，中英文）：发给**发起人**、模型的**启用的流程管理员**；结果是自动通过、自动驳回、转给上级或流程管理员时，**被处理待办的原办理人**也收到（他不再收到"待办已取消"）。只提醒与处理失败时，原办理人收到的是 `wf.task.overdue`。其余通知照常：新办理人收到"新待办"，被连带取消的其它待办收到"待办已取消"，实例结束时发起人收到"已通过/已驳回"，退回发起人时收到"已退回"。
- **已办列表**不把系统的处理算在原办理人名下；只提醒之后由本人处理的任务照常出现在已办里。

| 结果           | 意见键                       | 文字（中文）                                                                                             |
| -------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------- |
| 自动通过       | `seed.wf.timeout.autoPass`   | 超时未处理，系统已自动通过                                                                               |
| 自动驳回       | `seed.wf.timeout.autoReject` | 超时未处理，系统已自动驳回                                                                               |
| 转给上级       | `seed.wf.timeout.toManager`  | 超时未处理，系统已转给办理人的上级                                                                       |
| 转给流程管理员 | `seed.wf.timeout.toAdmin`    | 超时未处理，系统已转给流程管理员                                                                         |
| 无人可转       | `seed.wf.timeout.remindOnly` | 超时未处理，且没有可以转交的人，已提醒办理人；请有流程管理权限的人员在"任务管理"中改派                   |
| 处理失败       | `seed.wf.timeout.failed`     | 超时自动处理失败（例如下一个审批节点没有审批人），已提醒办理人；请有流程管理权限的人员在"任务管理"中改派 |

## 处理失败

自动通过或驳回推进到的下一个节点没人可审（`WF_NO_ASSIGNEE`）、退回目标无效、业务处理器拒绝等业务错误：这一条的处理整体回滚，再另开一个事务记一条结果为"处理失败"的 `timeout` 事件，办理人收到超时提醒，发起人与流程管理员收到 `wf.task.timeout`；之后按普通提醒继续，下一轮**不重复**处理。管理员修好流程或组织架构后，在"任务管理"里改派一次：改派清空提醒标记并重新计时，任务重新进入自动处理。

其它错误（数据库死锁、连接中断、代码缺陷）只回滚这一条，下一轮重试，不影响其它任务。每次运行的输出在定时任务日志里，例如 `reminded 2, timed out 3, timeout failed 1, errors 1 of 7`。

## 并发与多实例部署

每条待办在自己的事务里处理：先锁住实例行，再复查"仍是待办、已到期、未被处理过"，不满足就什么都不写；任务的状态更新是带条件的更新，不命中即回滚。所以与用户同时操作（用户先：系统跳过；系统先：用户的操作得到 409）、多个应用实例同时运行定时任务、候选列表已过期，都**只处理一次**。

## 流程管理员需要的权限

模型的"流程管理员"（`manager_user_ids`）只是通知对象，本身没有查看或改派实例的权限。通知正文是自足的（模型、编号、节点、到期时间、处理结果）；要处理这类通知（打开实例、在"任务管理"中改派），还需给他们的角色授予 **`wf.instance.view`**（查看实例）与 **`wf.task.manage`**（改派任务、终止实例），连同打开"实例管理""任务管理"菜单所需的 `wf.instance.browse`、`wf.task.browse`，并让其数据范围覆盖相应发起人的部门（两个管理页按发起人部门过滤）。
