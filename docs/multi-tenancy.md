# 多租户：启用与运维

多租户让一套部署服务多家公司（租户）：所有租户共用一个 MySQL 库，租户自有的每一行带 `tenant_id`，服务端自动按会话的租户过滤。开关默认关闭，关闭时就是原来的单租户系统，一切数据属于内置的默认租户（`id=1`，编码 `default`，同时是平台运营方）。本文说明如何打开开关、管理租户与套餐、平台人员进入租户、做两租户验收，以及编写租户感知的项目代码。设计依据与已知上限见[多租户设计说明](design-notes.md#tenancy)。

## 开关

开关是环境变量 `APP_MULTI_TENANT`（写在 `apps/server/.env`，不是秘密），只在启动时读取，默认 `false`；界面上没有开关，也不做运行时切换。改动后全部实例都重启才算切换完成，见[多实例部署](scale-out.md)。

| 项目               | 关闭（默认）                                                                                      | 打开                                                                                        |
| ------------------ | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 租户               | 只有默认租户可用；其他租户的数据保留，但无法登录                                                  | 已启用、未到期的租户都可用                                                                  |
| 登录页             | 没有租户编码                                                                                      | 主机名没有绑定租户时显示租户编码（留空即默认租户）                                          |
| 租户管理、租户套餐 | 侧栏与角色授权树不显示，接口 404；“菜单管理”照常列出这两页（同“系统接口”页随 Swagger 开关的做法） | 平台人员按权限点使用                                                                        |
| 日志页             | 与原来一致                                                                                        | 操作日志、登录日志多一列“操作者租户”；平台 root 在两张 API 日志页多出租户筛选与租户列       |
| 平台页             | 默认租户里持有平台菜单的角色照常使用                                                              | API 访问日志、API 错误日志与缓存列表只限平台 root；其他平台页对默认租户里的这些角色照旧可用 |

- **打开**：全新安装可以一开始就打开；已有库分两次部署。步骤见[部署指南](deploy.md#打开多租户开关)。打开前先复核默认租户里持有平台菜单的角色，打开过开关的库不能回退到 `1.1.0` 之前的任何版本（含其间从主线导出的补丁版本）。
- **关闭**：关闭开关不改变任何租户的启用状态，再打开的那一刻，全部已启用、未到期的非默认租户立刻恢复可用。所以关闭前先在租户管理里停用或设到期所有不再服务的租户；关闭后其他租户的会话在下一次请求时结束（只开着实时连接的在约 60 秒内断开），数据原样保留。关闭期间，启动日志对仍启用的非默认租户打印 warn，可以在开关关闭时停用它们：

  ```sh
  cd /srv/qiwu/current/apps/server
  node --env-file-if-exists=.env.local --env-file-if-exists=.env dist/db/tenant-disable.js <编码…>
  ```

  命令幂等，只改这些租户的 `enabled`，开关打开时拒绝运行（那时在租户管理页停用，同时结束它们的会话）。

## 租户从哪里来

登录前的租户由服务端解析：先按请求的主机名精确匹配租户绑定的域名，匹配不上再取登录页填写的租户编码，留空即默认租户。解析结果只决定去哪个租户核对凭据，登录后的身份与租户取自核对通过的用户行，记在服务端会话里。**没有选择租户的请求头**：登录后，任何请求头、参数都不能改变或证明会话的租户；租户编码只在登录、短信等登录前入口用于定位核对凭据的租户。编码不存在、租户停用或到期，登录都与密码错误的响应完全相同，不能借此探测编码。

- 绑定了域名的租户，用户在自己的域名上登录，不填编码；别的租户的令牌在这个域名上回 401。平台人员用主域名。
- 主域名上用编码登录时，同一浏览器同一时间只能登录一个租户（刷新令牌的 cookie 按主机名只有一个）。
- App 与小程序的 API 地址在构建时固定，只能用编码登录；小程序静默登录不需要编码，见[移动端](mobile.md#多租户租户编码)。
- 注册只对默认租户开放。

## 租户管理

“系统管理 → 租户管理”是平台页面（只有默认租户的人员能用），权限点 `iam.tenant.browse`、`view`、`create`、`modify`、`enter`、`reset-password` 可以分别授予默认租户里的平台人员，root 隐含全部。

**开通**一次完成：建租户行，运行租户级种子（以租户名命名的根部门、内置角色 `tenant_admin`、流程模板等），在用户配额内建管理员（持 `tenant_admin`、首次登录须改密）并记为所有者，任一步失败整体回滚。表单字段：

| 字段         | 说明                                                                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 编码         | 3–32 位小写字母、数字与中间的 `-`，字母开头；保留字（`default`、`www`、`api`、`admin` 等）不可用；创建后不能改，永不复用                 |
| 名称         | 列表与横幅显示的名称                                                                                                                     |
| 套餐         | 必选，只列已启用的套餐                                                                                                                   |
| 到期日       | 空为永久                                                                                                                                 |
| 用户配额     | 空为不限；后台新建、导入、注册都在同一事务里核对                                                                                         |
| 绑定域名     | 零到多个（最多 20 个），小写、不含端口与通配符；平台自己的主机名（当前请求的主机名与 `CORS_ORIGIN` 里的主机名）422，已被别的租户绑定 409 |
| 品牌名、logo | 侧栏、登录页、锁屏页与浏览器标题显示租户自己的名称与 logo；默认租户不设时显示原来的品牌                                                  |
| 管理员       | 用户名、显示名、手机号、邮箱                                                                                                             |

开通结果只显示一次初始密码：它既是管理员的首个密码，也是该租户后台新建或导入用户而不填密码时用的初始密码（每个租户各自随机生成，服务端只存密文）。“重置初始密码”重新生成这个租户的初始密码并显示一次，不改已有用户的密码。

**修改**的效果：

- 停用：立刻结束该租户的全部会话与实时连接，之后登录被拒；重新启用即恢复。
- 到期时间：改到不晚于当前时间等同停用；把永久改为将来某日，已有会话在那一刻失效；延长到期时间不延长已有会话（重新登录即可）。
- 换套餐：已登录的用户在下一次请求时按新套餐重载权限。
- 域名：去掉的域名立即可以绑给别的租户；主机名到租户的查找有 60 秒缓存，改绑最多 60 秒后生效。
- 默认租户不能停用、不能设到期时间或套餐，编码不能改，也没有租户初始密码（仍用参数 `iam.user.initial_password`），这些操作回 422；它的品牌与域名可以改。

**租户从不删除**：没有删除接口，也没有清除租户数据的命令。不再服务的租户停用或让它到期，数据原样保留，登录不了，后台任务也不处理它的数据；重新启用或续期即恢复。

## 租户套餐

“系统管理 → 租户套餐”决定一个租户能用哪些菜单（权限点 `iam.tenantPackage.*`）。可选的只有不属于平台的菜单；新生成的模块与管理员新建的项目菜单默认不在任何套餐里，要让租户使用就勾进套餐。

- 套餐只在服务端强制：租户用户的权限 = 角色授权 ∩ 套餐（平台权限点一律去掉），侧栏菜单同样如此；浏览器隐藏菜单不算授权。各租户的 `tenant_admin` 的权限就是套餐的全部权限点。
- 角色授权树只列套餐里的菜单。套餐缩小后，角色原有的授权行保留但不生效，再放大自动恢复。
- 只要求登录、属于某个功能分组的接口（如流程的待办与我的流程）在套餐不含该分组时回 404。`GET /api/auth/me` 的 `features` 列出会话可用的顶层菜单分组（开关关闭时不带这个字段），移动端据此隐藏功能。聊天不受套餐控制。
- 非默认租户没有套餐、或套餐被停用或删除时，什么都不能用（不是“不受限”）。停用的套餐不出现在开通表单里；被租户使用的套餐不能删除（409）。
- 改套餐的菜单、启用或停用套餐、给租户换套餐，都让全部已登录用户在下一次请求时重载权限。
- 默认租户不受套餐限制。

## 平台人员进入租户

进入租户是排查与代办的唯一跨租户入口，也是平台人员查看其他租户操作日志、登录日志的唯一方式。

- **授权**：给默认租户里的平台人员授予 `iam.tenant.enter`（root 隐含持有）。进入后数据范围仍按本人角色计算，本人角色的部门规则引用的是默认租户的部门，所以给这类人员配一个 `data_scope=all` 的角色，否则在目标租户里看不到数据。
- **进入**：在租户列表点“进入”并填写原因（必填，最多 200 字），整页重载后顶部常驻横幅“正在以平台人员身份操作租户 X，所有操作记入审计”与“退出租户”按钮，锁屏页同样提示。只有网页后台的会话能进入（移动端与第三方令牌不能）；停用、过期的租户也能进入（用于排查）。
- **权限**：用本人的权限，去掉平台权限点（所以非 root 在目标租户里用不了平台页面），不按目标租户的套餐收窄；root 仍是全部权限。进入者不是目标租户的管理员：所有者与 `tenant_admin` 持有者等受保护用户照旧只有 root 能改。
- **退出**：点横幅的“退出租户”。2 小时后、开关关闭后、本人的进入权限被撤销后，下一次请求自动退出；退出登录或会话被结束时同样记为退出。非 root 进入期间不能再进入别的租户，须先退出；root 直接进入另一个租户时先记一次退出。
- **仍在本人租户的部分**：个人资料、改密、表格偏好、我的站内信、公告、我的待办与我的流程，以及全部平台页（字典、参数、存储、模板等），进入期间仍在默认租户里运行，写入不会落到目标租户。实时连接只在本人租户的房间里。
- **多个标签页**：网页每个请求都带当前页面所属的租户；另一个标签页进入或退出租户后，旧标签页的请求回 409 并整页重载，不会把写入落到别的租户。

**审计**：

- 进入、退出各记一条操作日志（模块 `iam.tenant`，动作 `enter`、`leave`），记在默认租户，目标租户 id 在业务 ID 一列；进入的参数含原因与限时，退出的参数含原因（主动退出、切换、到期、开关已关闭、权限已撤销、退出登录、会话结束）。默认租户里同样删不掉这两类记录，只由保留期任务清理。会话自然过期没有退出记录：这时以进入记录里的限时与会话到期两者较早者为结束。`enter`、`leave` 两个动词不论开关如何都在操作日志的动作字典 `audit.verb` 里。
- 进入期间目标租户里的操作日志记在目标租户，并记下操作者的租户；目标租户的管理员看得到这些行，标为“平台”，IP、地点、浏览器与部门已遮蔽，也删不掉、清空不掉。
- 进入期间的每个请求（含查看）都写入 API 访问日志，不受访问日志参数与排除路径影响；完整的来源信息只在这里，只有平台能看。

## 智能体接入（MCP）

启用[智能体接入](mcp.md)（`APP_MCP=true`）时：

- **令牌属于用户所在的租户**：个人访问令牌建在用户本人的租户里（平台人员进入别的租户期间新建的也一样），调用时只在该租户里运行，绝不读请求头选租户；绑定了域名的租户，其令牌只能在自己的域名或主域名上用，别的租户的域名回 401。OAuth2 令牌按授权码所属的租户。
- **进入租户的状态不经 MCP 使用**：控制台会话不是 MCP 令牌；平台人员的个人令牌始终在默认租户里运行，看不到所进入租户的数据。
- **权限**：令牌用户本人的权限点，非默认租户的用户按其套餐收窄；工具页“MCP 工具”是平台页（`@PlatformOnly()`），对全部租户生效；“访问令牌”页属于租户，租户管理员（套餐含该页即持有 `mcp.token.browse` / `mcp.token.revoke`）只看得到、吊销得了本租户的令牌，别的租户的令牌回 404。
- **租户停用**：租户被停用或到期时间提前到当前之前时，其全部令牌随会话一起永久吊销；重新启用后须重新签发。
- 令牌摘要全局唯一（服务端生成的随机值，不会跨租户冲突），不需要释放。

## 全局唯一值的释放

租户不删除，所以全局唯一的值要逐项释放：

- **绑定域名**：在租户管理里编辑该租户、去掉域名即释放。
- **小程序微信号**：一个微信号只能绑定一个租户里的一个账号。停用、到期的租户（以及开关关闭时的非默认租户）仍占用其用户绑定的微信号。要释放，由持进入权限的平台人员进入该租户，删除对应的用户，或在用户管理里重置该用户的密码（重置会解除他的全部微信绑定；非 root 的进入者只能重置角色都在自己授予范围内的用户）。所有者与 `tenant_admin` 持有者的密码只有平台 root 能重置，所以他们绑定的微信号只有平台 root 能释放。没有按租户批量释放的操作。
- **公众号 AppID**（启用公众号模块时）：一个 AppID 在全部租户里只能接入一个存活的账号；新建账号前先用提交的 AppSecret 向微信换一次令牌，证明添加者持有这个公众号，失败不占用。占用中的 AppID 只有删除该账号才释放：平台人员在租户列表按 AppID 查出占用的租户（`iam.tenant.browse`），由持进入权限的平台人员进入该租户、在「账号管理」删除账号；停用、到期的租户同样如此。
- **开关关闭时**要释放，先临时打开开关：打开前按启动日志的 warn 确认不再服务的租户都已停用（没停用的先用上文的 `tenant-disable.js` 停用），再打开开关、全部实例重启，进入租户处理完后关闭开关、再次全部重启。

## 两租户验收

自动化用例：服务端 `apps/server/test/e2e/tenant-*.e2e-spec.ts` 在开关打开的测试应用里建出第二个租户，核对隔离、登录、套餐、进入租户与审计；Web 的租户通道 `pnpm --filter @qiwu/web e2e:tenant` 以开关打开启动服务端跑浏览器流程。`pnpm ci:local` 两者都跑；单独跑某一个，例如 `pnpm --filter @qiwu/server test tenant-isolation.e2e`。

上线前在与生产隔离的环境里手工走一遍：

1. 打开开关并重启；建一个不含流程的套餐，用它开通租户 B（绑定一个测试域名），记下初始密码。
2. 在主域名用 B 的编码登录 B 的管理员：强制改密；菜单只有套餐里的页面，没有流程与平台页。
3. 在 B 新建用户与业务数据，编码与默认租户里已有的相同；默认租户里看不到它们，B 里也看不到默认租户的。
4. 在绑定域名上不填编码登录 B；默认租户的令牌在这个域名上回 401。
5. 平台 root 进入 B（填写原因）：横幅出现，读写落在 B；退出后横幅消失。默认租户的操作日志里有进入、退出两条；B 的管理员看得到平台人员的操作，来源信息已遮蔽。
6. 停用 B：B 的会话立即结束、登录被拒；重新启用后恢复，数据原样。

## 已知上限

- 一个微信号只能绑定一个租户里的账号；一个公众号 AppID 只能接入一个租户，删除账号才释放；主域名上同一浏览器同一时间只登录一个租户。
- 改套餐、换套餐都让全部会话重载一次权限（权限版本是全局的一个计数）；租户很多时再改为每租户一个计数。
- 主机名到租户的查找有 60 秒进程内缓存，改绑域名最多 60 秒后生效。
- 平台人员看其他租户的操作与登录日志只能先进入该租户；没有平台跨租户的日志视图（登录日志里未解析出租户的行除外：平台 root 有只读筛选）。
- 品牌只有名称与 logo；favicon、`index.html` 的静态标题与 App 图标保持统一。
- 更多上限见[设计说明](design-notes.md#tenancy)。

## 编写租户感知的项目代码

以下规则开关关闭时同样成立：代码按多租户写，关闭开关只是让所有请求都在默认租户里运行。

**新建的表默认是租户表**。迁移里带 `tenant_id bigint unsigned NOT NULL`，唯一键以它开头（`UNIQUE (tenant_id, order_no, alive)`），没有唯一键的表加 `KEY idx_<表名>_tenant (tenant_id)`；实体用 `@TenantColumn()` 映射这一列。ORM 对租户表的读、写、计数、子查询与 join 自动加当前租户的条件，插入时写入当前租户，root 与 `@SkipDataScope()` 都跳不过。确实由平台统一维护、所有租户共用的表，登记进项目自己的 `apps/server/src/db/project-tables.ts` 的 `PROJECT_PLATFORM_TABLES`；必须全局唯一的键登记进同一文件的 `PROJECT_GLOBAL_UNIQUE`，并写明释放方式（`none`：值本身全局唯一，不会冲突；`row-delete`：删除该行才释放；`takeover`：写入方跨租户接管旧行）。`core/db/tenant-tables.ts` 只放模板自己的表，把两边合并成 `PLATFORM_TABLES` / `GLOBAL_UNIQUE`；项目不改它，升级模板时也就不会在这里冲突（见[升级模板版本](upgrade.md)）。迁移测试按规则检查全部表：不是平台表的表必须有必填的 `tenant_id`，唯一键以它开头，除非登记为全局键；项目新增表与迁移不需要改模板的测试。生成器的约定见[代码生成指南](codegen.md#建表软删除与引用约定new-tables)。

**原始 SQL 不经过 ORM**，须自己写租户条件，`pnpm verify` 的 `tenant-sql` 检查会报出漏写：

- 每张租户表各带自己的条件：`<别名>.tenant_id = ?`，join 进来的表也要；原条件里有顶层 `OR` 时先整体加括号，再 `AND` 租户条件。
- `INSERT` 租户表写 `tenant_id`。
- 确需跨租户的语句，在语句上或紧上一行写 `qw:cross-tenant <理由>`。
- 动态拼接的 SQL 在 `arch-allow: sql-concat` 注释里写明它怎样留在租户内（`tenant: <说明>`）。
- 租户表不支持 ORM upsert（`orUpdate`、`repo.upsert`）与 `clear()`：先按键读再更新或插入，删除用 QueryBuilder；涉及租户表的 `@ManyToMany` 会让服务拒绝启动，关联表用 `core/db/links.ts` 或映射成实体。

**按租户的定时任务**：在 `allTenants` 下扫描，扫描查询本身只取可用租户的行（已启用、未到期，开关关闭时只有默认租户；不能取出后再跳过，否则有条数上限的批次会被不可用租户的积压占满），再对每一行用 `withTenant(<行的租户>, …)` 处理；一个租户失败只记录，不影响其余租户。`withTenant`、`allTenants` 的每处调用都写 `qw:cross-tenant <理由>`。参考 `modules/workflow/runtime/wf-remind.ts`。

**Redis 键**一律经 `core/redis/cache-namespaces.ts` 构造，每个命名空间声明租户维度：

- `tenant`：用租户内才唯一的自然键（用户名、手机号、邮箱、编码、名称）建键。构造函数自动在命名空间后加租户段，默认租户同样加；扫描模式同样带租户段；在 `allTenants` 下构造即抛错。
- `global-id`：只用全局唯一的值（会话 id、令牌摘要、全局数字 id、AppID）建键，或有意跨租户共用的计数（按手机号、IP 的限流，在声明处注释原因）。
- `platform`：所有租户共用的数据（字典、参数、任务锁）。

**实时推送**按租户发：发给某个租户的全体用 `toTenant(tenantId(), …)`，没有发给所有租户的方法，见[实时推送](realtime.md)。

**任务队列**：用 `QueueService.add` 添加任务，它把当前 `tenantId()` 写进任务数据，上下文里没有租户时抛出 `TenantContextMissing`；处理器继承 `TenantJobProcessor`，`handle` 在任务所属租户的 `withTenant` 里执行，没有合法租户的任务立即失败、不重试。只处理平台表的工作用 `registerQueue({ name, platform: true })` 声明平台级队列，它的任务不带租户、处理时也没有租户。队列监控页含所有租户的任务，开关打开时只有平台 root 能打开。见[任务队列](queue.md)。

**公开路由**（`@Public()`）没有会话，开关打开时请求里没有租户：在 `apps/server/test/e2e/tenant-public.e2e-spec.ts` 的清单里登记它的租户来源（登录解析、会话、授权码、资源行、渠道凭据或只读平台数据），漏登记的公开路由遍历用例失败；运行时漏写来源的公开路由一碰租户表就是 500，不会落到默认租户。

**平台页面**：表在 `PLATFORM_TABLES` 里的页面，把 `route_name` 加进 shared 的 `PLATFORM_ONLY_ROUTES`，控制器每个带权限点的路由加 `@PlatformOnly()`（生成的控制器已加）。

**项目的租户级种子**：每个租户都需要的基础数据放进 `apps/server/src/db/seeds/project/tenant.seed.ts` 的 `PROJECT_TENANT_SEEDS`，开通租户时与每次 `pnpm db:seed` 对各非默认租户运行，只补缺少的行，见[从模板创建新项目](new-project.md)。

**测试**：生成的端到端用例已带两租户隔离用例（`test/setup/tenants.ts` 的 `createTenant` 建出第二个租户，`afterAll` 里 `dispose()`）；手写的接口照此至少为每个端点写一条跨租户 404。
