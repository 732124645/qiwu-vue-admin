# 租户扩展点与改造清单

v1 没有租户隔离。现有业务表没有 `tenant_id`，会话、CLS、缓存、文件和任务也没有租户上下文；部门数据权限不能当作租户边界。[数据范围设计](design-notes.md#data-scope)保留了规则链与生成器调用钩子，尚未实现多租户登录、数据分区、套餐或跨租户管理。

## 当前的两个空扩展点

[data-scope.ts](../apps/server/src/core/data-scope/data-scope.ts) 的 `defaultScopeRules()` 返回 `[deptScopeRule(), tenantRule]`。`tenantRule` 目前是 `() => {}`，不会增加 WHERE 条件。`BaseCrudService.scopedQb()` 调用这条规则链；生成器的 [服务模板](../apps/server/codegen-templates/server/service.ts.ejs) 继承基础 CRUD/tree 服务，复用同一空 hook。模板没有自动生成有效的 `tenantId` 列、参数或验证。

现有 [BaseEntity](../apps/server/src/core/db/base.entity.ts)、[CLS](../apps/server/src/core/context/cls.ts) 与 [Principal](../apps/server/src/core/auth/principal.ts) 没有租户字段。`applyScopes` 当前对 root 与 `@SkipDataScope()` 直接返回，不执行后续规则。将来只往 `tenantRule` 填过滤条件仍不够：须明确系统任务、root 以及跨租户操作的授权，防止沿用部门范围豁免而绕过租户隔离。

## 多租户需要的十项改造

以下依次列出；仅第 2、9 项的空 hook 已存在，其余均是后续设计与实施事项，需要迁移和授权回归。

| 顺序 | 改造项                                               | 当前状态与实施时必须核对的边界                                                                                                                |
| ---- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 所有业务表加 `tenant_id` 并入 `BaseEntity`           | 未实现。先确定存量行归属、平台公共表和租户业务表的范围，再迁移、回填和建立引用规则；追加日志等非 `BaseEntity` 表也要逐一盘点                  |
| 2    | 规则链追加 `tenantRule`                              | 已有 no-op。实现后须覆盖列表、详情、导出、options、写前锁、引用检查和原始 SQL；租户过滤与部门权限必须共同成立                                 |
| 3    | 唯一索引以 `tenant_id` 前导                          | 未实现。包含现有 `alive` 复合唯一索引；明确编码/名称是平台唯一还是租户内唯一，避免查询和 upsert 跨租户匹配                                    |
| 4    | 会话 payload 与 CLS 加 `tenantId`，登录按域名/头解析 | 未实现。租户必须由服务端验证并绑定会话；请求头不能直接成为可信租户身份。切换、刷新、OAuth 授权和权限缓存需一致校验                            |
| 5    | Redis key 增加 `t:{tenantId}:`                       | 未实现。全部经 `cache-namespaces.ts` 构造；同时处理现有 `qw:` ACL、命名空间、会话/权限版本/锁/限流/幂等键及清理范围，不能在业务代码里散拼前缀 |
| 6    | 定时任务按租户扇出                                   | 未实现。另行选择 `@TenantScopedJob` 或 handler 内循环；每次进入/退出租户上下文，锁、去重、补偿和日志均按租户核对                              |
| 7    | 文件路径前缀 `{tenantId}/`                           | 未实现。本地与 S3、直传、确认、下载、删除、附件绑定都需验证租户及属主；路径前缀本身不代替鉴权                                                 |
| 8    | 种子按租户执行                                       | 未实现。拆分平台级与租户级角色、菜单、字典、参数和管理员初始化，定义每租户幂等键，不能把已有全局种子反复裸执行                                |
| 9    | 生成器模板输出租户相关占位                           | 已有复用规则链的空 hook。实际列、DTO、索引、引用、controller、测试和模板 golden 都要随第 1–8 项同步更新，不能把今天的生成产物当作已隔离       |
| 10   | 菜单/套餐、超管跨租户与审计                          | 未实现。明确套餐白名单和跨租户管理员动作，审计记录 `tenant_id`、操作者及目标租户；浏览器菜单隐藏不是服务端授权                                |

计划中的 `t:{tenantId}:` 是未来租户键结构，不能直接替换当前受 `qw:*` ACL 约束的部署前缀。Redis Pub/Sub 不按库号自动隔离，现有 `socket.io:<REDIS_DB>` 与 `job:sync:<REDIS_DB>` 频道只分隔部署；未来租户房间/频道的授权与隔离仍须设计。部署多实例的已有能力和限制见 [scale-out.md](scale-out.md)，它不提供租户隔离。

## 实施顺序与授权回归

先确定租户来源、平台数据归属和跨租户管理合同，再落实表结构/存量回填与唯一索引。会话、CLS 与规则链接通后，继续落地 Redis、任务、文件、种子、生成器和菜单/审计；上线前完成所有入口的隔离与回归。不能仅添加列和一条 WHERE 条件就启用租户功能。

至少用两个租户、相同业务编码、相同部门/角色结构验证：

- A 的列表、详情、导出、选择器不返回 B 的记录；A 对 B 的 id、混合批量、引用、附件、导入 upsert 和业务动作不能读写，并核对落库无副作用。
- 伪造/遗漏租户头、跨租户刷新令牌、OAuth 授权码或 Socket 连接被拒；缓存、会话撤销、锁、限流和幂等不串租户。
- root 与系统任务只按新合同跨租户；任务失败恢复、通知收件人、共享存储、种子重跑和套餐/菜单权限保持隔离；审计能还原目标租户。
- 部门权限的五种 scope、all/any 合并、越界 404、授权子集以及生成器 golden 继续通过，见 [数据权限](data-scope.md)。

这些是后续多租户改造的验收要求，目前没有对应的租户功能测试通过记录。迁移、数据回填、租户创建和生产启用应作为独立工作经授权实施。
